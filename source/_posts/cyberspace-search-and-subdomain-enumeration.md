这次作业有三个任务，本文按顺序对应：

- **任务一**：找出与 ZoomEye 功能类似的搜索引擎；

下面先回答第一个问题，再用同一组关键词做一次跨平台对照，最后把子域名收集拆成“被动”和“主动”两条线。

## 一、和 ZoomEye 类似的搜索引擎

ZoomEye 属于网络空间搜索引擎。它和普通网页搜索的区别在于：普通搜索主要索引网页内容，而网络空间搜索引擎还会索引主机、端口、服务 banner、页面标题、证书、组件指纹等资产特征。因此，它更适合回答“互联网上有哪些资产暴露了某种服务或特征”，而不只是“哪个网页提到了某个词”。

和它定位相近的平台，常见的有下面这些：

| 平台 | 官方入口 | 定位与特点 |
| --- | --- | --- |
| ZoomEye | <https://www.zoomeye.ai/> | 网络空间搜索引擎，可按标题、组件、IP、域名等条件检索暴露资产 |
| FOFA | <https://fofa.info/> | 网络空间测绘系统，提供语法检索、结果统计和 API |
| Shodan | <https://www.shodan.io/> | 官方定位为面向互联网连接设备的搜索引擎，强调服务 banner 与设备暴露面 |
| Censys | <https://censys.com/> | 可检索主机、Web 属性和证书数据，并提供攻击面管理能力 |
| 360 Quake | <https://quake.360.net/> | 360 网络空间测绘平台，按 IP、域名、服务、组件等维度检索 |
| Hunter（鹰图） | <https://hunter.how/> | 奇安信的网络空间测绘鹰图平台，面向资产发现与风险排查 |

需要说明两点：

1. 这些平台的数据来源、扫描频率、指纹规则和查询语法并不相同，不能用一次结果数量直接判断谁“更全”。
2. 它们提供的是“某资产曾被观察到具有某特征”的线索，不等于该资产存在漏洞，也不等于可以直接访问。真正下结论前还需要授权范围内的验证。

## 二、用 `title:"后台"` 做一次跨平台检索

### 2.1 为什么选标题

`title` 查的是 HTML 页面中的 `<title>` 内容。很多后台登录页会把“后台管理”“后台登录”写进标题，所以 `title:"后台"` 常被用来做初步筛选。

但这个条件很粗：标题里出现“后台”的页面，可能是正常的登录入口，也可能是一篇介绍后台开发的文章、一个 404 页面，甚至是蜜罐。它只能作为线索，不能直接当作“存在未授权后台”。

### 2.2 ZoomEye 的检索结果

在 ZoomEye 输入 `title:"后台"`（输入框显示时会带转义反斜杠），得到下面的结果页：

![ZoomEye 检索 title:"后台" 的结果页](/images/cyberspace-search/zoomeye-title-backend.png)

*图 1：ZoomEye 检索 `title:"后台"` 的结果页，截图时间 2026-11-04。页面显示约 136,959 条结果，其中最近一年数据 41,241 条，用时 1.546 秒。*

页面首条结果是 `mallnmore.com:80`，标题为“后台登录”。从 Header 可以看到它返回 `HTTP/1.1 301 Moved Permanently`，并跳转到 `https://mallnmore.com/`；页面还标出了 Cloudflare、AS13335 和 2026-11-04 16:04 的观测时间。这些信息说明 ZoomEye 记录的不只是网页正文，还包括协议响应、组织、ASN 等资产上下文。

### 2.3 FOFA 的检索结果

把同样的关键词放到 FOFA：

![FOFA 检索 title:"后台" 的结果页](/images/cyberspace-search/fofa-title-backend.png)

*图 2：FOFA 检索 `title:"后台"` 的结果页，截图时间 2026-11-04。页面显示 161,758 条匹配结果、54,790 个独立 IP，耗时 2,772 ms，并限定在最近一年。*

首条结果是一个标题为“后台管理”的站点，页面同时给出了 IP、地理位置、ASN、域名、发现时间和 `nginx/1.15.7` 等信息；第二条结果则带有 Alikunlun、Chinanet 等上下文。和 ZoomEye 相比，FOFA 在结果卡片里更直接地展示了归属与组件信息。

### 2.4 两组结果能说明什么

把两张截图放在一起看：

| 项目 | ZoomEye | FOFA |
| --- | --- | --- |
| 检索词 | `title:"后台"` | `title:"后台"` |
| 页面显示结果 | 约 136,959 条（最近一年 41,241 条） | 161,758 条匹配（54,790 个独立 IP，最近一年） |
| 页面显示耗时 | 1.546 秒 | 2,772 ms |
| 首条结果特征 | `mallnmore.com:80`，301 跳转，标题“后台登录” | 标题“后台管理”，`nginx/1.15.7`，带 IP 与归属信息 |

两个平台用了同一个关键词，数量却不一样。这并不能证明“谁漏掉了更多资产”，因为索引范围、扫描时间、去重方式和查询解析都可能不同。更稳妥的做法是：

- 用多个平台做交叉验证，而不是只信一家；
- 把标题条件和组件、状态码、证书、地理条件等组合起来，缩小误报；
- 对结果只做“公开展示信息”的整理，不绕过授权去访问或测试。

如果从防守方视角看，这类检索也有价值：企业可以用自己的域名做限定，检查哪些后台页面已经被测绘平台收录，再决定是否通过 VPN、零信任、访问控制或双因素认证收敛暴露面。

## 三、子域名收集：从证书日志到 DNS 枚举

子域名收集的目标，是把一个主域名下可能存在的资产尽量找全，例如 `mail`、`vpn`、`test`、`admin`、`oa` 等前缀。常见做法可以分成两类：

- **被动收集**：查询别人已经公开或已经索引的数据，不直接向目标发请求；
- **主动收集**：自己构造候选子域名，做 DNS 解析和 HTTP 探测。

### 3.1 被动收集：证书透明度日志

证书透明度（Certificate Transparency，CT）日志会公开记录签发的 TLS 证书，而证书里通常包含域名或子域名。`crt.sh` 是常用的 CT 日志查询入口，因此很适合做子域名的第一轮被动收集。

![crt.sh 的 Identity Search 页面](/images/cyberspace-search/crtsh-certificate-search.png)

*图 3：crt.sh 的 Identity Search 页面，以 `www.google.com` 做精确查询，截图时间 2026-11-04。查询类型为 Identity，匹配方式为 ILIKE，结果中可以看到多条 Common Name 为 `www.google.com` 的证书记录。*

这张截图展示的是“按证书查域名”的基本用法，但要注意：查询词是精确的 `www.google.com`，所以结果主要也是这个主机名，并不等于已经枚举出了 `google.com` 的全部子域名。实际做子域名收集时，通常会把查询词改成带通配符的形式，例如：

```text
https://crt.sh/?q=%25.example.com
```

这里的 `%` 是 ILIKE 匹配中的通配符，`%25` 是它在 URL 里的编码。查询后还需要：

- 展开证书里的 SAN（Subject Alternative Name），不要只看 Common Name；
- 把结果去重、转成小写，去掉 `*.` 通配符和不合法的域名；
- 记录来源和时间，方便后面复核。

CT 日志的局限也很明显：没有签发过公开证书的内部域名不会出现；通配符证书可能只暴露一个 `*.example.com`；证书历史也不等于当前仍然存活。

### 3.2 被动收集：网络空间搜索引擎

除了证书日志，还可以用 FOFA、ZoomEye、Quake、Hunter 等平台按域名或证书维度检索。例如 FOFA 可以用 `domain="example.com"` 查与某个域名相关的资产；其他平台也有各自的域名、站点或证书语法，具体写法要以平台当前的语法说明为准。

这一路线的优点是结果自带标题、端口、组件、归属等上下文，适合快速判断“这个子域名像什么”。缺点是只能看到已经被平台收录的资产，不能保证覆盖全量。

### 3.3 主动收集：字典枚举与 DNS 解析

主动收集通常会准备一份常见子域名字典，把 `www`、`mail`、`vpn`、`test` 等前缀和根域名拼接，再逐个做 DNS 解析。下面这张截图使用的是 Layer 子域名挖掘机 5.0（SAINT SEC 更新版）：

![Layer 子域名挖掘机的枚举界面](/images/cyberspace-search/layer-subdomain-bruteforce.png)

*图 4：Layer 子域名挖掘机对 `google.com` 做演示性枚举的界面，截图时间 2026-11-04。截图时状态栏显示“已发现88个域名，进度1048/164374”，任务仍在运行；这里的 `google.com` 仅用于工具界面演示，实际练习应替换为自己控制或已获授权的域名。*

从界面可以读到这些信息：

- 目标域名是 `google.com`，端口设置为 `80,443`，并勾选了“扫描端口”和“服务器信息”；
- DNS 为 `DNSPOD-119.29.29.29`，线程为“全速”，同时勾选了“枚举”和“接口”；
- 结果表的“来源”列显示为“暴力枚举”，说明核心动作是字典拼接加 DNS 解析；
- `m.google.com` 解析到 `142.251.45.139`，80/443 显示 `sffe` 和“80: 正常访问”；
- `www.google.com` 解析到 `104.244.42.197`，但工具显示“端口未开放”；
- `sandbox.google.com` 解析到 `74.125.195.81`，80 端口返回“80: (404) 未找到”；
- `corp.google.com` 解析到 `192.178.163.129`，80 端口返回“80: (400) 错误的请求”。

这里有三个容易误读的点：

1. **截图时的 88 个不是最终结果。** 进度才到 1048/164374，任务还在跑，不能写成“google.com 只有 88 个子域名”。
2. **DNS 能解析，不代表 Web 一定可用。** `www.google.com` 在截图里显示端口未开放，可能是超时、被拦截或探测策略限制，不能据此断言服务不存在。
3. **“全速”不适合真实项目。** 高并发会给目标 DNS 和 Web 服务带来压力，也可能触发防护；实际测试应降低线程、加延迟，并严格限定在授权范围内。

### 3.4 一套可复用的流程

把上面的方法串起来，可以整理成一套偏工程化的流程：

1. **先定边界**：确认域名归属和书面授权，列出要覆盖的根域名，记录开始时间。
2. **被动打底**：用 crt.sh 查证书，用 FOFA、ZoomEye、Quake、Hunter 查域名相关资产。
3. **主动补充**：用字典做 DNS 枚举，先检测泛解析，避免把 `*.example.com` 的泛解析结果当成真实子域名。
4. **存活验证**：对解析成功的域名做 HTTP/HTTPS 请求，记录状态码、标题、证书和跳转关系；不要顺手做未授权的漏洞扫描。
5. **整理结果**：统一字段，例如域名、解析 IP、CNAME、开放端口、HTTP 状态、标题、来源、发现时间。
6. **人工复核**：把 CDN、云服务、泛解析、停放页和失效记录单独标注，避免把“解析成功”直接等同于“有效资产”。

| 方式 | 代表工具/平台 | 优点 | 局限 |
| --- | --- | --- | --- |
| 证书日志 | crt.sh | 被动、速度快，能发现历史证书中的域名 | 只覆盖被 CT 日志记录的证书 |
| 网络空间测绘 | ZoomEye、FOFA 等 | 有标题、端口、组件等上下文 | 只覆盖平台已收录的资产 |
| 字典枚举 | Layer 等 | 能补充未被收录的子域名 | 依赖字典和 DNS，会产生真实请求 |

## 四、几点总结

第一，ZoomEye、FOFA、Shodan、Censys、Quake、Hunter 这类平台的核心价值，是把互联网上的资产特征变成可检索的索引。它们适合做资产发现和暴露面梳理，但不是“漏洞验证器”。

第二，`title:"后台"` 这样的条件适合做粗筛，不适合直接下结论。相同的查询词在不同平台出现不同数量，是数据源和索引差异的正常表现，应该交叉验证，而不是简单比较大小。

第三，子域名收集要区分被动和主动。证书日志和测绘平台适合先铺面，字典枚举适合补点；最终结果一定要做泛解析排除、存活验证和人工复核。比“收集到多少个”更重要的是：每个结果从哪里来、什么时候发现、是否在授权范围内。

最后再强调一次：本文的截图只用于教学分析。对公网目标做端口扫描、目录探测或漏洞验证之前，请确认自己拥有目标，或已经拿到明确的书面授权。
